# 0.4.0 RAG 检索实验台设计与评测说明

> 版本：0.4.0  
> 日期：2026-09-09  
> 当前引擎：`bm25-zh-v1`

## 目标

在连接 Embedding、向量数据库和大模型之前，先建立一个可运行、可解释、可自动评测的关键词检索基线。输入问题后，用户需要看见系统找到了哪些文本块、为什么命中、来自哪里，以及没有足够依据时为何拒绝返回结果。

## 架构与数据边界

```text
浏览器 / Electron IndexedDB
  └─ 已授权 KnowledgeChunk
       └─ POST /api/retrieval/search
            └─ 本机 FastAPI + Jieba + BM25
                 └─ 排序结果、分数拆解、来源位置
                      └─ 前端展示并把检索摘要写回 IndexedDB retrievals
```

- 知识来源、正文和文本块仍以客户端 IndexedDB 为唯一持久化位置。
- FastAPI 每次只处理本次请求中的已授权文本块，不建立服务器数据库，也不保留请求内容。
- 检索记录保存在客户端，包含查询、命中文本块、耗时、引擎、查询词和最高分。
- 当前不生成向量、不调用大模型、不上传远程服务。

## 排序方式

`bm25-zh-v1` 使用 Unicode NFKC 和小写化规范文本，通过 Jieba 搜索模式切分中文，同时保留英文、数字与常见技术词。最终分数由以下可解释部分组成：

1. 正文 BM25 分数；
2. 资料标题命中加权；
3. 章节标题命中加权；
4. 完整查询短语命中加权；
5. 查询词覆盖度加权。

多词问题如果只在标题中命中一个宽泛词、正文完全没有命中，则返回“查询覆盖度不足”，防止将弱相关结果包装成可靠依据。

## API

- `GET /api/health`：服务版本、检索引擎和无持久化声明。
- `POST /api/retrieval/search`：接收查询、Top K 和可追溯文本块，返回排序结果与分数拆解。
- OpenAPI：启动服务后访问 `http://127.0.0.1:8000/docs`。

请求限制：查询不超过 500 字、单次最多 2,000 个文本块、语料总量不超过 800 万字符、Top K 为 1～10。

## 起步评测

运行：

```bash
npm run eval:retrieval
```

数据集位于 `server/evals/dataset.json`，包含 9 个脱敏样例文本块、18 条可回答查询和 2 条无答案查询。2026-09-09 本机运行结果：

| 指标 | 结果 |
|---|---:|
| Hit@1 | 1.0000 |
| Recall@5 | 1.0000 |
| MRR@5 | 1.0000 |
| 无答案识别准确率 | 1.0000 |
| P50 服务端检索耗时 | 约 2.4 ms |
| P95 服务端检索耗时 | 约 3.7 ms |

该集合只用于验证接口、排序规则和回归稳定性，规模小、主题明确，不能代表真实业务检索质量。下一阶段应从公开或脱敏资料中人工标注 80～120 条查询，并报告关键词、向量、混合检索和重排之间的消融对比。

## 下一阶段接口边界

0.4.0 不预先声称具备语义检索。后续在保持现有响应结构的前提下增加：

1. Embedding Provider；
2. 向量数据库；
3. 关键词与向量的 RRF 融合；
4. Reranker；
5. 基于真实评测集的效果和延迟对比。
