# AI / RAG 数据基础构想与实施前确认记录

> 整理日期：2026-09-04  
> 当前项目版本：0.4.4
> 当前状态：知识数据底座、真实评测集、BM25、BGE + Qdrant、RRF 与 Cross-Encoder 重排已完成；行动快照与生成式 AI 尚未实施  
> 后续实施条件：检索层已通过独立保留集与端到端验收，下一阶段按 Provider 无关方式实施引用式 RAG 问答

## 1. 用户原始需求

> “AI/RAG 数据基础，这个要具体如何操作，先给出思路、过程，等我通知确认再落地。”

本次讨论的目标不是立即接入 AI，而是先明确：个人使用数据、个人知识库、RAG 检索和 AI 计划生成之间应如何分工，以及未来按什么顺序实现。

## 2. 核心结论

AI / RAG 能力应拆成三个相互独立的层次：

1. **个人行为数据层**：用本地固定规则汇总训练、专注、待办和启动数据。
2. **个人知识库与 RAG 层**：只检索用户主动授权的笔记和导入资料。
3. **AI 计划层**：综合结构化行动数据与检索到的知识片段，生成等待用户确认的计划草案。

整体数据流：

```text
个人行为数据 ──结构化统计──┐
                            ├─→ 上下文组装 → AI 计划草案 → 用户确认 → 写入计划
个人知识资料 ──RAG 检索─────┘
```

关键原则：训练、专注、待办等行为记录不需要全部向量化；它们更适合结构化统计。笔记和用户导入的资料才进入 RAG 知识库。

## 3. 两类数据通道

### 3.1 个人使用数据

建议纳入：

- 近 7 天、近 30 天的训练次数、正确率、反应时和难度变化。
- 现实专注时长、完成度和分心来源。
- 待办进入行动比例。
- 开始前抗拒程度。
- 直接开始与使用启动舱的行动路径。
- 下一步保留率。
- 当前目标、每日可用时间和偏好专注时长。

这些信息继续由本地规则计算，形成“个人行动快照”。AI 只接收经过筛选的统计摘要，不直接读取全部原始历史记录。

行动快照示例：

```json
{
  "period": "最近7天",
  "availableMinutesPerDay": 30,
  "focusSessions": 6,
  "averageCompletion": 72,
  "topDistraction": "phone",
  "startResistance": 2.3,
  "nextStepRate": 50,
  "stalledTodoCount": 2
}
```

### 3.2 个人知识库

当前第一版支持：

- 用户主动授权的个人笔记。
- 用户主动导入的 Markdown、TXT、Word DOCX 和文字型 PDF 文档。
- 用户明确选择的目标、项目说明或学习资料。

后续再考虑扫描 PDF OCR、网页收藏、历史计划与复盘、文件夹同步。

所有知识来源默认不开放给 AI。每条笔记或每份资料应提供“允许用于 AI / RAG”的独立开关。

## 4. 知识资料处理过程

每份获得授权的资料依次经过：

1. 提取正文。
2. 清理无效空白和重复内容。
3. 按标题和段落边界切分文本。
4. 为每个文本块保留来源和章节信息。
5. 生成关键词和语义向量。
6. 保存到本地检索数据库。

建议每个文本块约 300～700 个中文字符，前后重叠约 50～100 字。通过内容哈希判断资料是否变化，只重新处理修改过的内容。

建议的数据结构：

```ts
interface KnowledgeChunk {
  id: string
  sourceId: string
  sourceTitle: string
  content: string
  section?: string
  contentHash: string
  embedding?: number[]
  createdAt: string
  updatedAt: string
}
```

## 5. 存储设计

现有 `localStorage` 适合轻量应用状态，不适合保存大量文档和向量。建议分层存储：

- `localStorage`：继续保存用户设置和轻量应用状态。
- `IndexedDB`：保存知识来源、文本块、向量和检索记录。
- Electron 数据量明显增大后，再评估 SQLite。
- 模型密钥不得写入普通 `localStorage`。

预计新增的逻辑集合：

- `knowledgeSources`：知识来源信息。
- `knowledgeChunks`：分块后的文本。
- `knowledgePermissions`：资料授权状态。
- `retrievalHistory`：检索结果和引用记录。
- `aiPlanDrafts`：尚未采用的 AI 计划草案。
- `aiSettings`：模型方式和隐私设置。

应用轻量状态可能升级到 v11，但知识正文和向量应独立保存在 IndexedDB 中。

## 6. RAG 检索流程

以“帮我制定下周计划”为例：

1. 识别用户目标和计划时间范围。
2. 读取对应范围的结构化个人行动快照。
3. 对已授权知识库进行关键词检索。
4. 同时进行向量语义检索。
5. 合并、去重并重新排序候选片段。
6. 选取约 6～10 个最相关的知识片段。
7. 将知识片段、来源名称和行动快照组装为上下文。
8. 交给 AI 生成结构化计划草案。

所有检索结果都必须能够回到原始来源。计划页面需要明确显示引用了哪条笔记、哪份资料或哪项个人统计。

## 7. AI 计划输出设计

AI 不应直接返回无法约束的大段文本，而应输出结构化草案：

```ts
interface AIPlanDraft {
  objective: string
  period: string
  assumptions: string[]
  dailyActions: {
    date: string
    task: string
    firstStep: string
    completionDefinition: string
    plannedMinutes: number
    evidenceRefs: string[]
  }[]
  uncertainties: string[]
}
```

计划界面需要显示：

- 计划参考了哪些个人数据。
- 引用了哪些笔记或资料。
- 哪些内容属于模型推测。
- 哪些必要信息没有找到。
- “采用计划”“修改后采用”“放弃草案”三个明确操作。

只有用户确认后，计划才能写入每日计划或待办。AI 不能自动覆盖现有安排。

## 8. 模型连接方式

建议先定义统一接口，不在业务代码中绑定单一模型厂商：

```ts
interface AIProvider {
  generatePlan(input: PlanContext): Promise<AIPlanDraft>
  createEmbeddings(texts: string[]): Promise<number[][]>
}
```

后续可选择：

- 本地向量模型与远程生成模型组合。
- 全本地模型。
- 用户自备 API。
- 自建安全服务端代理。

当前网站为纯前端应用，公共 API 密钥不能写入源码。若以后使用远程 AI：

- Electron 版可通过主进程和系统凭据保存密钥。
- 浏览器版应使用安全后端代理，或由用户临时提供自己的密钥。
- 只发送检索到的必要片段和结构化摘要，不上传整个知识库。

## 9. 推荐实施阶段

### 第一阶段：数据底座，不连接 AI

建议优先实施：

- 新增知识库管理入口。
- 用户选择哪些笔记可用于知识库。
- 支持导入 TXT、Markdown。
- 使用 IndexedDB 保存知识数据。
- 建立文本分块和增量更新机制。
- 建立个人行动快照。
- 提供“检索测试器”，输入问题后查看找到的原始片段。
- 检索结果显示原始来源。

第一阶段验收标准：即使没有 AI，也能验证输入一个问题后，系统是否找到正确资料。

### 第二阶段：RAG 计划草案

检索验证可靠后再实施：

- 接入统一 AI Provider。
- 生成结构化的一周计划草案。
- 每条建议显示数据依据和知识引用。
- 提供采用、修改和放弃。
- AI 不直接修改待办和每日计划。

### 第三阶段：个人行动实验（已取消）

2026-09-14 路线调整后，本阶段不再实施，也不再作为求职版 1.0.0 的完成条件。项目不会新增实验同意、基线/干预窗口或主观实验反馈采集；现有行动洞察仍只描述本地历史记录，不宣称因果。

## 10. 明确不采用的做法

- 不把每次点击和全部行为数据向量化。
- 不在无法查看检索结果时直接接入 AI。
- 不自动把所有私人笔记交给模型。
- 不让 AI 直接覆盖待办、计划或知识内容。
- 不根据少量记录判断“最适合的方法”。
- 不生成医学诊断、人格判断或能力标签。

## 11. 当前进度与后续事项

0.3.4～0.3.7 已完成知识来源、存储、文本处理与 DOCX/PDF 提取；0.4.0～0.4.3 已完成关键词基线、真实评测、本地向量、混合召回与重排；0.4.4 已完成平台无关的引用式 RAG 代码与本地上下文预览：

- 知识库入口位于“设置”页，没有新增顶层导航。
- 个人笔记默认不授权，可逐篇加入、取消或同步最新快照。
- 支持导入、查看、更新和移除 TXT、MD、Markdown 文档。
- 知识正文保存在本地 IndexedDB，浏览器版和 Electron 版使用各自的数据空间。
- 页面显示知识来源数量、授权笔记数、导入文档数和本地占用空间。
- 删除个人笔记或清空设备数据时会同步清理相应知识来源。
- 独立知识库已升级为 IndexedDB v2，并拆分为 `sources`、`permissions`、`chunks`、`retrievals`、`metadata` 五个对象仓库。
- 知识来源保存时使用 Web Crypto 生成 SHA-256 内容校验值；来源正文发生变化时自动清除其旧文本块，避免后续索引继续引用过期内容。
- 删除单项来源会在同一事务内级联删除授权和文本块；全量清空会清除来源、授权、文本块和检索记录，同时保留数据库结构元数据。
- 0.3.4 的 IndexedDB v1 会自动迁移到 v2，保留原有知识正文，并补齐独立授权记录和 SHA-256 校验信息。
- 设置页可查看数据库版本，以及授权记录、文本块、检索记录和向量数量；检索记录会随查询写入，向量数量来自本地索引状态。
- TXT、个人笔记和 Markdown 会在本机提取正文；Markdown 支持 ATX/Setext 标题、自然段、列表、引用、链接、强调和代码围栏的第一版处理。
- 文本按章节和段落边界组合，常规块控制在约 300～700 字；短章节保留独立块，避免跨章节拼接。
- 每个文本块保存资料名称、完整章节路径、原文起止行、字符起止位置、字符数、内容哈希、来源哈希和处理器版本。
- 来源 SHA-256 与已有文本块匹配时直接复用；只处理正文发生变化、缺块或处理器版本变化的资料。
- 设置页显示每份资料的分块数量，并可预览各块正文、章节与原文位置。
- Word DOCX 使用 Mammoth 在本机提取标题、段落、列表和表格，转换后进入既有章节分块流程。
- 文字型 PDF 使用 Mozilla PDF.js 在本机读取文字层，按页保存正文、总页数和“第 N 页”章节位置。
- DOCX/PDF 原始二进制不会写入 IndexedDB；单文件限制 10 MB，提取正文限制 4 MB。
- 没有文字层的 PDF 会提示需要 OCR，不会保存为空知识来源；扫描 PDF OCR 暂未实施。
- 本机 FastAPI 服务支持 BM25、BGE 向量、RRF 混合召回和多语言 Cross-Encoder 重排，返回完整排序轨迹、来源位置和耗时。
- 用户明确构建后，Qdrant local mode 保存已授权文本块与 512 维向量；支持 SHA-256 语料指纹、增量同步、过期索引阻断与清除。
- 已建立 15 份真实项目文档、100 条人工标注查询，固定划分 20 条开发集与 80 条独立评测集。
- 保留集最佳模式 Recall@1 为 0.4533、Recall@5 为 0.7933、MRR@5 为 0.5891、nDCG@5 为 0.6383、拒答准确率为 1.0000。
- 引用式 RAG 已支持 6,000 字符上下文预算、`S1`～`S8` 引用、来源位置、疑似提示注入标记、结构化输出和引用白名单校验。
- 已依据官方文档实现 DeepSeek 对话补全、Bearer 鉴权与 JSON Output 适配；单样本真实 API 冒烟测试已返回带 `S1` 引用的结构化回答。未注入 Key 时仍可本地预览上下文，真实生成按钮保持禁用。

尚未实施：

1. DeepSeek 正常、拒答、冲突证据与提示注入场景的完整真实生成评测。
2. 结构化个人行动快照。
3. 桌面端安全凭据存储与模型设置界面。
4. 一周计划草案、引用依据和用户确认写入流程。
5. 真实生成质量评测、知识库独立导出与恢复。

下一步完成 0.4.4 的多类型真实生成评测并冻结版本标签；通过后进入 0.5.0 个人行动上下文。
